## 1. Bug Crítico — MARGEM CRÍTICA spam + saldo errado

### Sintoma
Bot enviou "MARGEM CRÍTICA — TUDO FECHADO" 4 vezes seguidas com rácios de 526%, 532%, 917%, 341%.
Saldo reportado: 0.17 USDC. Saldo real na app Binance: ~240 USDC, rácio real: 2.97%.

### Causa
Conta EU/BNFCR mantém o capital em BNFCR, mas `get_balance()` e `get_margin_ratio()` só liam o primeiro activo USDC encontrado na resposta da API — que era dust de 0.17 USDC.

- `get_balance()`: retornava na primeira correspondência com `mb > 0` → devolvia 0.17 USDC (dust)
- `get_margin_ratio()`: dividia `maintMargin` USDC (~0.89, das posições USDC-M) por `marginBalance` USDC (0.17) = 526%
- Adicionalmente havia um `break` prematuro que impedia a leitura do activo BNFCR

### Fix (`exchange.py`)
Ambas as funções passaram a **somar USDC + BNFCR** em vez de retornar na primeira correspondência:
```python
for a in data.get("assets", []):
    if a.get("asset") in ("USDC", "BNFCR"):
        total += float(a.get("marginBalance") or ...)
```

### Fix secundário (`execution.py`) — spam de alertas
Adicionado cooldown de 300 segundos para o alerta MARGIN_CRITICAL:
```python
if agora_mc - mem.get("margin_critica_ts", 0) > 300:
    mem["margin_critica_ts"] = agora_mc
    tg("🚨 MARGEM CRÍTICA...")
```

## 4. Melhorias Aplicadas

### 4.1 ATR_PERIOD 14 → 8 (`config.py`)
Fontes convergem: ATR(8) para timeframes 5m responde mais rápido à volatilidade real.
ATR(14) é adequado para 15m+. Em scalping 5m, o período 14 introduz lag no SL sizing.

```python
# Antes
ATR_PERIOD = 14
# Depois
ATR_PERIOD = 8
```

### 4.2 Bug `total_trades` não actualizado (`execution.py`)
`total_trades` era incrementado em `abrir_trade` (abertura) mas nunca recalculado em `_registar_fecho` (fecho). Após restart da DB, ficava a 0 enquanto `wins/losses` mostravam valores reais.

```python
# Adicionado em _registar_fecho(), após actualizar wins/losses:
mem["total_trades"] = mem.get("wins", 0) + mem.get("losses", 0)
```
